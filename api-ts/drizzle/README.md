# drizzle/ migration notes

## Snapshot history gotcha: `agent_link_codes` (fixed 2026-08-01)

`meta/0012_snapshot.json` originally recorded a **stale, pre-hand-edit**
shape for `agent_link_codes` (`code_hash varchar(128)`, plain `timestamp`
columns, non-unique `ix_agent_link_codes_code_hash` index) even though the
migration's actual applied SQL (`0012_zippy_rachel_grey.sql`, hand-edited in
commit `60ddac66`) creates the table with `varchar(64)`, `timestamptz`
columns, and a UNIQUE `code_hash` index — matching
`src/db/schema/agentLinkCodes.ts`.

Because `drizzle-kit generate` diffs the *current* schema against the
**latest** snapshot (`0014_snapshot.json` as of this writing), not `0012`'s,
this stale entry was not actively dangerous for future generates — `0013`
and `0014`'s snapshots already reflect the correct, real applied shape. But
it left a landmine: any future migration that gets regenerated by diffing
back against an old baseline, or any tooling that reads `0012_snapshot.json`
directly, would see the wrong (pre-hand-edit) column types and could try to
"fix" them with a spurious `ALTER TABLE ... TYPE varchar(128)` /
non-unique-index rewrite against a live table that never had that shape.

**Fixed**: `meta/0012_snapshot.json`'s `agent_link_codes` entry was hand-
edited to match what `0012_zippy_rachel_grey.sql` actually applies
(`varchar(64)`, `timestamp with time zone`, unique index) — the same shape
already recorded in `0013_snapshot.json` / `0014_snapshot.json`.

**Rule going forward**: whenever a migration's `.sql` file is hand-edited
after `drizzle-kit generate` produced it (idempotency guards, dropped
unrelated diff, etc.), the corresponding `meta/NNNN_snapshot.json` must be
hand-checked too — `drizzle-kit` has no way to know the SQL and the snapshot
diverged. Diff the snapshot's affected table entries against what the SQL
you kept actually does, not against what was originally generated.
