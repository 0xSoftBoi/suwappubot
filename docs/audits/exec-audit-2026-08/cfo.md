## Findings

### [HIGH] Bridge/cross-chain swaps executed via USDT0 collect $0 platform fee, but the DB ledger records revenue as if the fee were charged
- **File:** `bot/services/swap_engine.py:1751-1756` (quote path omits `platform_fee_bps`), `bot/services/bridge/usdt0_api.py:359-390` (`amount_int` = full user amount, no fee deduction, no fee-recipient transfer), `bot/handlers/swap.py:1122-1131` (`fee_service.calculate_fee_with_price` computed unconditionally, independent of which provider will execute) and `bot/handlers/swap.py:1519-1534` (`fee_service.record_fee` posts that computed fee to `FeeTransaction` regardless of provider).
- **Issue:** `_get_usdt0_quote` is called without `platform_fee_bps` (contrast with `_get_propamm_quote`/Jupiter/Li.Fi calls a few lines above/below, which do pass it). USDT0 is a 1:1 LayerZero OFT mint/burn — `send_param`'s `amountLD` is the caller's full `amount_int`; there is no fee-collector leg, no separate transfer, no bps deduction anywhere in `_execute_usdt0_swap`. Meanwhile the swap handler computes `fee_amount/fee_percentage/fee_usd` once per quote via the tier rate, independent of provider, and posts it to `FeeTransaction` on every successful swap — including USDT0 ones. Net effect: the user's on-chain balance shows a 0%-fee transfer, but Suwappu's internal ledger (and `fee_sweeper.get_uncollected_fees()`) shows a phantom collected/uncollected fee that no wallet on earth actually holds.
- **Dollar impact:** Every dollar of USDT0-routed volume is a 100% miss against the tier rate (0.1–1.0% depending on tier) that would otherwise apply — real revenue leak, not just a bookkeeping error, since the user was never charged the amount recorded as "fee." At $50k/mo of USDT0-routed volume (plausible once the corridor is flipped on for Plasma/HyperEVM/Ink/Unichain/Berachain/Flare — chains with few other USD-stable rails) at the FREE-tier blended rate (~0.7%), that's **~$350/mo in phantom-recorded, never-collected revenue** — real money missing from any revenue dashboard built off `FeeTransaction`, and a swept-fee reconciliation that will never balance.
- **Note:** `near_intents` has a real fee mechanism (`appFees` in the 1-Click API, gated on `near_intents_fee_recipient`/`near_intents_fee_bps`, `bot/services/bridge/near_intents.py:159-184`), but `near_intents`/`allbridge`/`symbiosis`/`arbitrum_native` are all **quote-only** — `swap_engine.EXECUTABLE_PROVIDERS` (`swap_engine.py:86-97`) deliberately excludes them, so today they can't execute at all (good defensive design against mis-execution) and therefore can't currently mis-collect either. **USDT0 is the only one of this group that IS executable, and it's the one with zero fee wiring.**
- **Fix:** Either (a) don't quote/execute USDT0 until it has a fee leg (skim `fee_amount_token` off `amount_int` before `send()`, or add a second small `transfer()` to the fee collector on the source chain before the OFT send), or (b) if USDT0 is being kept fee-free as a deliberate low-cost-corridor loss-leader, stop calling `fee_service.calculate_fee_with_price`/`record_fee` for `quote.provider == "usdt0"` so the ledger stops recording revenue that was never collected. (a) is the money-positive fix; (b) is the minimum correctness fix. This is a MONEY-PATH change — route to `money-path-reviewer`.

### [HIGH] On-chain fee collection is silently a no-op unless `fee_collector_address`/`fee_collector_solana`/`jupiter_referral_account` are configured — never verified this session
- **File:** `bot/config/settings.py:1340-1399`, `bot/services/fee_service.py:72-74`.
- **Issue:** `fee_collector_address`/`fee_collector_solana` default to `None`. The settings docstring for `jupiter_referral_account` says outright: *"Leave unset to disable Solana fee collection (swaps still work, no platform fee taken)."* `swap_engine.py:1478-1483`'s own comment confirms: *"On-chain collection is still gated per-provider on a configured collector, so this is a no-op until collectors are set."* I did not verify (Railway env vars are out of scope for a file read) whether these are actually set in the `python-api` prod service.
- **Dollar impact:** If any of the three is unset in prod, 100% of swap volume on that chain-family collects $0 on-chain regardless of tier — same phantom-ledger failure mode as the USDT0 finding above, but for the entire EVM or Solana fee path, not one bridge corridor. This is the single highest-leverage number to pull before any other pricing/vendor decision in this audit.
- **Fix (immediate, not code — an ops check):** `deploy-ops`/`cso` should confirm `FEE_COLLECTOR_ADDRESS`, `FEE_COLLECTOR_SOLANA`, `JUPITER_REFERRAL_ACCOUNT` are set in the Railway prod `python-api` service and that the Jupiter referral token account has actually been created via the Jupiter Referral Program (a plain wallet address here breaks `/swap` per the docstring, so if it "works," it's very likely already correctly configured — but confirm, don't assume).

### [MEDIUM] Jupiter platform fees accrue to a referral token account that is never programmatically claimed
- **File:** `bot/services/fee_service.py:646-676` (`sweep_all_fees` comment: *"Jupiter — the platformFeeBps accrues to the referral token account (feeAccount); it must be CLAIMED via the Jupiter Referral Program to move it to the main treasury... This pass reconciles the internal ledger... it does NOT itself move tokens."*).
- **Issue:** No claim job was found anywhere in the codebase (`grep -r "claim" bot/services` for Jupiter Referral Program turned up nothing beyond this comment). `fee_sweeper` runs hourly and marks Solana-chain `FeeTransaction` rows `collected=True` purely as an internal reconciliation step — it does not call the Jupiter Referral Program's claim instruction. If nobody is manually claiming via Jupiter's UI on a cadence, Solana-side platform fees sit in the referral token account indefinitely (not lost, but also not liquid/usable revenue, and `collected=True` in the DB creates false confidence that it's already in the treasury).
- **Dollar impact:** Not a leak (funds aren't gone), but a liquidity/reporting gap — Solana swap fee revenue is invisible/unusable until someone claims it. Impact scales with Solana swap volume; flag for `cao` to confirm whether manual claims are happening and at what cadence.
- **Fix:** Add an automated (or documented manual, cadenced) Jupiter Referral Program claim step, and don't mark `collected=True` until the claim tx confirms.

### [MEDIUM] Points reward store sells a real ENTERPRISE-tier subscription (0.1% fee) for points, contradicting fee_service.py's own stated invariant that ENTERPRISE is contract-only
- **File:** `api-ts/src/db/schema/points.ts:432-440` (`'1 Month ENTERPRISE'`, 20,000 points, `rewardType: 'subscription'`, `rewardValue: 'enterprise'`), `api-ts/src/services/PointsService.ts:1065-1099` (subscription-reward redemption path — atomic points-debit + `subscriptions` table upsert, tier becomes real), `bot/services/fee_service.py:259-268` (comment: *"ENTERPRISE is contracted pricing, negotiated per customer... it is not something a consumer perk is allowed to move"* — this guardrail is enforced only inside `get_fee_decimal`'s points/positions-discount stacking, NOT against the subscription-grant redemption path, which writes `subscriptions.tier` directly).
- **Issue:** `get_fee_decimal` correctly refuses to let a `fee_discount` or Position-card perk touch ENTERPRISE. But the points **redemption store** has a completely separate code path (`redeem_subscription_reward` / `PointsService.ts` subscription branch) that buys ANY tier including ENTERPRISE outright with points, bypassing that guardrail entirely — because it's not a discount on the rate, it's a direct tier grant. `REDEMPTION_POINTS_PER_USD = 200` (`points.ts:447`) prices it consistently ($99.99 × 200 ≈ 20,000 — internally consistent), but the tier itself is earnable via `POINT_ACTIONS` (`points.ts:36-49`): `referral_signup` (500 pts) + `referral_first_swap` (200 pts) = 700 pts per referred account. **~29 referred accounts each doing one minimum ($1, `MIN_SWAP_USD`) swap would clear the 20,000-point ENTERPRISE threshold** without the ENTERPRISE tier ever being "negotiated" as the code's own commentary assumes it is. I did not verify anti-sybil controls on the referral system in this session (no self-referral / device-fingerprint / KYC check reviewed) — flagging as a real exposure, not a confirmed exploit.
- **Dollar impact:** If exploitable, a user with ~$29 of sybil-swap cost buys the 0.1% ENTERPRISE rate that is otherwise supposed to require a $99.99/mo negotiated contract — a 9x-per-swap-fee discount (1.0% FREE → 0.1% ENTERPRISE) obtained for a fraction of list price, indefinitely renewable at 20,000 pts/30 days. At even modest abuse (2–3 users/month), that's the ENTERPRISE contract price ($200–300/mo) never collected, plus those users trading at 10x-lower margin than intended on all subsequent volume.
- **Fix:** Either (a) explicitly accept this as an intentional "loyalty rebate, not the contracted-only comment in fee_service.py" and update the fee_service.py comment so it stops asserting a guarantee the codebase doesn't actually enforce, or (b) cap the points-redemption store at PREMIUM (mirroring the `get_fee_decimal` floor) and route `security-auditor`/`growth-marketing` to check whether referral sybil-farming is already rate-limited elsewhere (I did not find a control in the files reviewed this session).

### [LOW] Fee-tier "get Premium/Pro bps without paying" via points fee_discount reward — priced correctly, not a bug, but worth noting for completeness
- **File:** `api-ts/src/db/schema/points.ts:367-393` (`Fee Discount 0.1%` = 500 pts, `Fee Discount 0.2%` = 1000 pts, 7-day duration), `bot/services/fee_service.py:149-185` (`_active_fee_discount_fraction`).
- **Note:** This one is internally consistent — the discount is read as percentage-points-of-FREE-rate and applied proportionally, floored at the ENTERPRISE rate, and excluded on ENTERPRISE (per the extensive in-code derivation comment). No math bug found here; this is well-guarded relative to the earlier, more severe finding above (the subscription-grant path, which bypasses this guard entirely).

### [OK — no issue found] Core fee math (tier bps, 30% referral split, 40/60 staking/protocol split, rounding)
- **File:** `bot/services/fee_service.py:337-378` (`calculate_fee`).
- Rounding is `ROUND_DOWN` at 2 places (fee amount, referral reward) — both round in the protocol's favor (never overcharges, never double-pays a referrer), and the 40/60 split is computed on `net_fee` (post-referral) so `referral + staking + protocol == fee_amount` exactly — the code comment is correct that splitting gross would over-allocate to 130%. `get_fee_decimal`'s discount stacking (points × positions × referee-rebate, each floored/capped) is multiplicative not additive, so no combination of stacked discounts can reach zero or go negative — `ABSOLUTE_FLOOR = 2bps` is unreachable in practice per the code's own worked example (ENTERPRISE + card + referee rebate = 5.4bps). No double-charge or skipped-fee path found in this file itself — the leak is entirely at the bridge-provider boundary (see HIGH findings above), not in the fee math.

### [OK — no issue found] x402 credit pricing (`billing.ts`) — no negative-balance path found
- **File:** `api-ts/src/routes/billing.ts:254-346` (Stripe credit grant), `api-ts/src/config/constants.ts:107-113` (`CREDIT_PACKS`).
- Credits are granted additively via an idempotent Stripe-webhook transaction (`consumedPayments` unique-constraint guard + `onConflictDoUpdate` balance increment) — replay-safe. `$/credit` is consistent and disclosed: `starter` 1:1, `growth` $100→$110 (10% bonus), `scale` $500→$600 (20% bonus) — a real, increasing bonus for larger packs, not a hidden markup. I did not review the credit **consumption/debit** path in `agent.ts` (out of primary scope this session, and the file is large — 3000+ lines); if a negative-balance exposure exists it would be in the debit path (`agent.ts` swap-execute credit-consumption), not in `billing.ts`'s grant path reviewed here. Flag for a follow-up pass if credit-debit correctness needs its own audit.
